## ⚠️ 边界声明：与 su-memory-sdk 的职责区隔

本计划书的所有任务**严格限定在世界模型引擎（CPU）职责范围内**，不侵入记忆引擎（su-memory-sdk）的领域。

| 职责 | 归属 | 本计划是否涉及 |
|------|------|--------------|
| 因果发现 / 干预 / 反事实推理 | **MCI World Model（本项目）** | ✅ P0-1 |
| JEPA 时序状态预测 | **MCI World Model（本项目）** | ✅ P0-3 |
| 三元路由决策 | **MCI World Model（本项目）** | ✅ P0-1 |
| 医疗数据标准解析（FHIR→内部结构） | **MCI World Model（本项目）** | ✅ P0-2 |
| 短期/长期记忆存储与检索 | su-memory-sdk | ❌ 不涉及 |
| 经验回放 / 案例库持久化 | su-memory-sdk | ❌ 不涉及 |
| 向量索引 / zvec 存储 | su-memory-sdk | ❌ 不涉及 |
| 跨会话状态持久化 | su-memory-sdk | ❌ 不涉及 |

**关键原则**：
- `patient_history` 指的是**本次推理的 clinical 输入数据**（体征时序矩阵），不是持久化记忆
- `ClinicalDecisionEngine` 是**无状态编排层**（每次调用独立），不维护跨调用状态
- 如需跨会话记忆，通过 `adapters/su_memory_bridge.py`（已有）对接，不在本计划中扩展
- `discover()` 是**从输入数据即时计算因果图**，不是从记忆库检索历史因果图

## P0-1：三模块集成（第 1-5 天）

### 1.1 问题诊断

代码级证据（三个模块互相不调用）：

| 调用方 → 被调方 | ClinicalTriRouter | MCIWorldModel | MedicalCausalSDK |
|----------------|-------------------|---------------|------------------|
| ClinicalTriRouter | — | ✗ 不调用 discover/intervene | ✗ 不调用 diagnose |
| MCIWorldModel | ✗ 不调用 route/infer | — | ✗ 不调用 diagnose |
| MedicalCausalSDK | ✗ 不调用 route | ✗ 不调用 discover/intervene | — |

**后果**：WorldModel 能发现的因果图喂不到 Router；Router 的路由决策结果传不到 MedicalSDK 做合规校验。

### 1.2 集成方案：ClinicalDecisionEngine 统一入口

新建 `src/mci_world_model/sdk/_clinical_decision_engine.py`，作为三大模块的编排层：

```
临床查询输入
    │
    ▼
┌──────────────────────────────────────────────┐
│         ClinicalDecisionEngine               │
│                                              │
│  1. WorldModel.discover() → 因果图 G_clin    │
│     （从患者历史数据发现因果关系）            │
│                                              │
│  2. WorldModel → CausalDAG 转换              │
│     （因果边列表 → DAG 结构，喂给 Router）    │
│                                              │
│  3. ClinicalTriRouter.route(query)           │
│     （三元路由：物理/因果/语义）              │
│                                              │
│  4. 按路由结果执行：                          │
│     - PHYSICAL → WorldModel.jepa_predict()   │
│     - CAUSAL   → WorldModel.intervene()      │
│     - SEMANTIC → KnowledgeBase.query()       │
│                                              │
│  5. MedicalCausalSDK.diagnose()              │
│     （因果诊断 + 证据校验 + 合规检查）        │
│                                              │
│  6. 输出 ClinicalDecision（含审计轨迹）       │
└──────────────────────────────────────────────┘
```

### 1.3 核心接口设计

```python
@dataclass
class ClinicalDecision:
    """统一临床决策输出。"""
    # 路由决策
    route_type: RouteType
    route_confidence: float
    safety_level: SafetyLevel
    need_review: bool

    # 推理结果（按路由类型填充）
    prediction: dict | None      # PHYSICAL: JEPA 预测
    causal_effect: dict | None   # CAUSAL: 干预效应
    knowledge: dict | None       # SEMANTIC: 知识检索

    # 因果诊断（MedicalSDK）
    diagnosis: CausalDiagnosis | None

    # 合规校验
    compliance: ComplianceReport | None

    # 全程审计
    audit_trail: list[dict]      # 从 discover → route → infer → diagnose 全链路
    timestamp: str


class ClinicalDecisionEngine:
    """临床决策引擎 —— 三模块编排层。"""

    def __init__(
        self,
        world_model: MCIWorldModel,
        router: ClinicalTriRouter,
        medical_sdk: MedicalCausalSDK,
        knowledge_base: SemanticKnowledgeBase,
        compliance_engine: ComplianceRuleEngine | None = None,
    ) -> None: ...

    def decide(
        self,
        query: ClinicalQuery,
        patient_history: list[dict] | None = None,  # 本次推理的临床输入（非持久化记忆）
    ) -> ClinicalDecision:
        """端到端临床决策。

        流程：
        1. discover → 从患者历史发现因果图（若提供 history）
        2. build_dag → 因果图转 CausalDAG，注入 Router
        3. route → 三元路由决策
        4. execute → 按路由类型执行对应推理
        5. diagnose → MedicalSDK 因果诊断 + 合规校验
        6. 返回 ClinicalDecision（含全程审计）
        """
```

### 1.4 实施步骤（逐日拆解）

| 天 | 任务 | 交付物 | 验证标准 |
|----|------|--------|---------|
| D1 | 新建 `_clinical_decision_engine.py` 骨架；定义 `ClinicalDecision` dataclass | 文件 + 数据类 | 语法检查通过 |
| D2 | 实现 `_build_dag_from_state()`：`CausalWorldModelState.causal_edges` → `CausalDAG` 转换器 | 转换方法 + 单元测试 | 10 条因果边能正确转为 DAG |
| D3 | 实现 `decide()` 主流程：discover → build_dag → route → execute 四步编排 | 主方法 | mock 数据跑通 3 种路由 |
| D4 | 接入 MedicalCausalSDK：诊断 + 合规校验；全链路审计日志 | 完整 decide() | 审计轨迹含 5 个步骤 |
| D5 | 端到端测试 + 集成测试；写 `test_clinical_decision_engine.py` | 10+ 项测试 | 全部通过 |

### 1.5 关键技术决策

- **因果图转换**：`CausalWorldModelState.causal_edges` 格式是 `[{"cause": str, "effect": str, "rho": float, ...}]`，需转为 `CausalDAG` 的邻接表 + 符号权重
- **懒加载策略**：`discover()` 开销大，仅在提供 `patient_history` 时调用；无历史时用预置 DAG\n- **无状态设计**：`ClinicalDecisionEngine` 不持有跨调用状态，避免侵入记忆引擎职责
- **线程安全**：复用 `MCIWorldModel._discover_lock`，避免并发状态污染
- **审计格式**：每步记录 `{"step": str, "input": ..., "output": ..., "duration_ms": ...}`

### 2.4 核心接口

```python
class FHIRAdapter:
    """FHIR 标准 → 内部数据结构适配器。"""

    def parse_patient_bundle(
        self, bundle: dict
    ) -> PatientContext:
        """解析 FHIR Bundle（Patient + Observation 列表）。

        Args:
            bundle: FHIR Bundle JSON，含 Patient 和 Observation resources

        Returns:
            PatientContext（患者元信息 + 生命体征时序矩阵）
        """

    def to_clinical_query(
        self, patient: PatientContext, question: str
    ) -> ClinicalQuery:
        """将患者上下文 + 自然语言问题转为 ClinicalQuery。"""

    def to_patient_timeline(
        self, observations: list[dict]
    ) -> PatientTimeline:
        """FHIR Observation 列表 → PatientTimeline（兼容 MIMIC benchmark 格式）。"""


@dataclass
class PatientContext:
    """患者上下文（FHIR 解析后的内部表示）。"""
    patient_id: str
    age: int
    gender: str
    weight_kg: float | None
    diagnoses: list[str]        # ICD-10 代码列表
    vital_signs: np.ndarray     # (T, V) 体征时序矩阵
    vital_names: list[str]      # 变量名列表（与 LOINC 映射对齐）
    medications: list[dict]     # 用药记录（药名 + 剂量 + 时间）
    lab_results: list[dict]     # 检验结果
    timestamp_range: tuple[float, float]
```

## P0-3：JEPA 在 MIMIC 波形数据上验证（第 4-7 天）

### 3.1 目标

证明 JEPA 物理路径预测器在**真实生理时序数据**上有效，不只是合成数据。

### 3.2 实验设计

**数据源**：MIMIC-III 临床数据库的 Chartevents 表（已有访问权限框架）

**实验变量**（7 维体征，与 ClinicalQuery.patient_state 对齐）：
- 心率 (HR)、收缩压 (SBP)、舒张压 (DBP)、血氧 (SpO2)、呼吸频率 (RR)、体温 (Temp)、GCS

**预测任务**：
- 输入：过去 12 个时间窗的体征矩阵 `state ∈ R^{12×7}`（1 小时历史）
- 输出：未来 3 步体征预测 `pred ∈ R^{3×7}`（15 分钟前瞻）

**评估指标**：

| 指标 | 公式 | 目标 |
|------|------|------|
| MAE | 平均绝对误差（各维度） | < 体征标准差的 50% |
|方向准确率 | 预测趋势方向正确率 | > 70% |
|相对 MAE | MAE / 体征均值 | < 0.15 |
|物理约束违反率 | 预测值超出生理可行范围的比例 | < 5% |

### 3.3 实施方案

新建 `scripts/jepa_mimic_validation.py`：

```
1. 数据加载：MIMIC-III Chartevents → PatientTimeline（复用已有 MIMIC 框架）
2. 窗口切片：滑窗 (T=12, V=7) → 训练集/测试集
3. JEPA 训练：JEPAPhysicsAdapter.fit()（已有接口）
4. 预测评估：多步前向预测 × 4 指标
5. 基线对比：LinearPhysicsPredictor（已有）vs JEPA
6. 输出报告：docs/jepa-mimic-validation-report.json + .md
```

### 3.4 关键技术决策

- **数据访问**：复用 `benchmarks/real_world/mimic_causal_benchmark.py` 的数据加载逻辑，不重新造轮子
- **降级方案**：若无 MIMIC 物理访问权限，用 `benchmarks/real_world/` 中的半合成数据（Sachs/Tuebingen 已有）
- **Seed 固定**：`SEED=42`，保证可复现（AGENTS.md 要求）
- **NaN 处理**：MIMIC 真实数据有缺失值，需前向填充 + 均值插补

## 不做什么（P0 边界）

明确排除以下内容，避免范围蔓延：

**功能边界**：
- 不做不确定性量化（P1-1）
- 不做真实临床指南灌入（P1-2）
- 不做多中心验证（P2-1）
- 不做 SaMD 合规申报（P2-2）
- 不修改现有模块的核心逻辑，只新增集成层和适配层

**su-memory-sdk 边界（严守）**：
- 不在本项目中实现任何记忆存储 / 检索 / 持久化逻辑
- `ClinicalDecisionEngine` 设计为无状态编排层，不维护跨调用状态
- 不扩展 `adapters/su_memory_bridge.py`（记忆桥接属 su-memory 侧职责）
- 不引入 `lite_pro` / `SuMemory` 依赖（世界模型独立运行，记忆引擎可选挂载）
- 如需经验复用 / 案例库，走现有桥接适配器，不在世界模型核心新增存储
